重點說明

  • 系統只有兩種使用者：前台消費者和後台管理員。管理員分角色，observer 只能看，不能改（api.py:85、api.py:162）。
  • 外部只會呼叫 LLM，實際只用到兩個「槽位」：nlu（需求理解）和 reply（回覆生成）。test_connection 是後台按「測試」才會觸發的連線檢查。

關鍵資料流：用 5 個案例走完整個系統

每個案例都是「使用者做了一件事 → 系統一步一步怎麼處理」，5 個合起來會用到系統裡的每一個模組

先看鳥瞰：一輪對話分成 5 個階段

LLM 呼叫外部模型 程式 確定性程式碼 讀 DB 讀資料庫 寫 DB 寫資料庫 瀏覽器 前端畫面

💡 記住一句話：LLM 只負責「聽懂」和「說出來」（階段 ① 和 ⑤），中間「篩哪幾台、排第幾名、下一步問什麼」全部由程式碼決定。

這些數字是怎麼來的？我用系統真正的函式（importer、domain、scoring、cards、pipeline）加上內附的 371 台模擬 CSV 實際跑了一遍，所以台數、排名、權重都是程式算出來的，不是編的。 只有兩個地方是示意：案例 1 的「模型輸出」（真實模型每次回答可能略有不同）和「模型寫的回覆」。另外，資料庫改用種子預設值代替，價格單位是人民幣。
🧑 「預算 8000 以內，要剪 PR」

新使用者在空白對話裡打的第一句話。這個案例會走過完整的 11 步，是最主要的一條路徑。

UserAppapi.tsapi.pysecuritypipelinellmdomainscoringcardsanimationPostgreSQL
  1. 1程式收訊息、驗身分

    前端 api.ts 送出 POST /api/conversations/{cid}/messages。後端 require_user 從 Cookie lg_session 解出 JWT，確認是誰、對話是不是他的。expire_idle 順便把閒置超過 30 分鐘的對話標成結束。

    { "text": "預算 8000 以內，要剪 PR" }
  2. 2LLM需求理解：把一句話變成結構化需求

    pipeline.nlu_parse 把「nlu 提示詞 v1 + 目前需求檔案（空的）+ 軟體目錄」組成一段 prompt，透過 llm.complete("nlu") 送給模型（溫度 0.1）。模型照提示詞規定只回 JSON：

    示意{
  "ops": [{ "kind": "hard", "field": "budget", "label": "預算 8000 以內" }],
  "software": [{ "raw": "PR", "canonical": "Premiere Pro" }],
  "missing": ["edit_intensity"],
  "weight_suggestion": { "deltas": { "performance": 3 }, "confidence": 0.8 }
}

    接著程式做校正：normalize_item 把「預算 8000 以內」解析成 {"max": 8000}。預算屬於明確條件，所以強制設成 hard（硬條件），信心值設為 1.0。

  3. 3讀 DB軟體畫像：查 Premiere Pro 的門檻

    match_software 依別名（PR、premiere…）找到「Premiere Pro」，collect_software_rules 取出它的「4K 剪輯」用途設定：

    硬門檻（不夠就淘汰）記憶體 ≥ 16 GB、顯存 ≥ 6 GB
    建議值記憶體 32 GB、顯存 8 GB
    權重修正性能 +4、螢幕 +1、散熱 +1
    額外子分啟用「Premiere Pro 4K 剪輯」跑分（權重 14）
    還要問edit_intensity（剪輯強度）
  4. 4程式候選篩選：371 台逐台判定

    domain.snapshot 對每一台跑 classify，分成三種：正式候選、邊界候選（差一點，保留但標註）、淘汰。

    預算規則：容差是 max(8000×8%, 500) = 640。價格超過 8640 淘汰，8000～8640 算邊界。

    全部
    371

    邊界

    淘汰
    284

    淘汰原因：超出預算 187 台、顯存不滿足軟體門檻 64 台、兩者都有 33 台。
    邊界範例：ROG 魔霸新銳 2025（¥8499，「預算接近，屬於邊界候選」）。

  5. 5程式審批模型的權重建議

    模型建議「性能 +3」，信心值 0.8 ≥ 門檻 0.75，所以採用（命中規則 R014）。如果低於 0.75，這個建議會直接被忽略。模型只能「建議」，最後採不採用由程式決定。

  6. 6程式合成權重、算分、排序

    模型建議和軟體畫像的修正，都透過 scoring.rebalance 疊加，總和固定是 100。每台的產品力分 = Σ(維度分 × 權重) ÷ Σ權重，再依產品力由高到低排序。

  7. 7程式決定動作、挑追問卡

    正式候選 75 台 > 50，action_for_count 決定動作是 probe（追問）。pick_followup 用 rules 策略，從卡片目錄挑出條件符合、優先度最高的一張：

    🗨️ 你偶爾剪 4K 視頻時，屬於下面哪種情況呢？
    輕度剪輯中度剪輯重度剪輯
    card_edit_intensity · 優先度 450
  8. 8程式準備卡片資料

    這輪回傳 4 張卡片：requirements（新增 2 條需求）、software（Premiere Pro 門檻）、count（371 → 75，淘汰 284、邊界 12）、followup（上面那張追問卡）。

  9. 9LLM回覆生成：把算好的事實說成人話

    只把 facts（動作、台數、新需求、前三名、追問問題）交給 complete("reply")。提示詞明確禁止模型編造機型、分數或名次。

    示意好的，我記下了預算 8000 以內和 Premiere Pro。為了讓 PR 剪輯順暢，顯存不到 6G 的機型先排除了，目前有 75 台符合……想再確認一下你的剪輯強度。

    模型失敗時會改用 fallback_reply，實際輸出：「我記下了：預算 8000 以內、Premiere Pro。候選從上一輪收到 75 臺正式候選，另有邊界 12 臺。還差一個關鍵信息，想先確認一下。」

  10. 10瀏覽器播放動畫、更新畫面

    後端用 build_events 排好 13 個事件，前端 animation.playEvents 用 GSAP 依序播放：

    facts_readyreq_appearreq_flysoftware_hitpanel_openweights_autopanel_closecount_rollcards_dimscore_changereordertop3followup
  11. 11寫 DB寫完整記錄

    寫入 runs（每一步、模型呼叫的 tokens 與金鑰末 4 碼、前後權重、命中規則 R012 R003 R013 R014 R021 R022 R029 R011）和 messages × 2（使用者＋助手）。另外更新 conversations 的需求檔案、權重、正式台數 75，標題取前 24 個字。歷史記錄只能讀，任何修改請求都會被擋下（回 403）。

🧑 「預算 4000 以內、需要獨立顯卡、1kg 以下」

新對話，而且沒有設定模型金鑰。這個案例同時示範兩條特殊路徑：模型失敗時的降級，以及條件太嚴、一台都沒有的情況。

llm（ModelError）pipeline（heuristic_ops / relax_options / fallback_reply）domain.classify

降級路徑

  1. 2LLM模型呼叫失敗 → 改用關鍵字規則

    llm.complete 發現沒有金鑰，丟出 ModelError("未配置模型密鑰")。這一步在 runs 裡記成 error，然後改用 heuristic_ops，實際抽出 3 條硬條件：

    只要獨顯              (gpu = 獨顯, hard)
預算 4000 以內         (budget = {"max": 4000}, hard)
1kg 以下              (weight_kg = 1, hard)
  2. 4程式371 台全部淘汰
    全部
    371
    正式
    0
    淘汰
    371

    淘汰原因：超預算＋太重 272、超預算＋太重＋沒獨顯 83、太重＋沒獨顯 13、只是太重 2、超預算＋沒獨顯 1。重量容差是 +0.15 kg，所以超過 1.15 kg 就淘汰。

  3. 7程式0 台 → 動作 relax（建議放寬）

    relax_options 會試兩種放寬：拿掉尺寸、拿掉預算，看能多出幾台。這個案例沒有尺寸條件，而拿掉預算後重量條件還是會擋掉所有機型，所以得到的放寬選項是空的。

    ⚠️ 發現：放寬建議只會試「尺寸」和「預算」，不會試「重量」或「獨顯」。這種情況下 relax 卡片會沒有任何選項 → 待確認

  4. 9LLM回覆也失敗 → 用固定句型
    我記下了：只要獨顯、預算 4000 以內、需要獨立顯卡、1kg 以下、預算 4000 以內、需要獨立顯卡、1kg 以下。候選從上一輪收到 0 臺正式候選，另有邊界 0 臺。

    ⚠️ 發現：關鍵字規則會把「整句話」當成預算和重量的標籤，固定句型回覆因此出現重複文字 → 待確認（只有在模型失敗時才會發生）

🛠️ 第一次啟動系統，管理員登入後台、查看鏈路、發佈新資料

這個案例涵蓋前 4 個案例沒用到的部分：啟動腳本、種子資料、匯入器、登入驗證、後台。

一鍵啟動系統.batstart_local / pg_bootstrap / servemain.boot_dbseedimportersecurityAdminAppModelPagetrace.ts
  1. 1程式一鍵啟動

    一鍵啟動系統.bat → 安裝 uv → uv sync → start_local.py（.env 沒有金鑰就提示輸入）→ pg_bootstrap.py（第一次啟動會下載 PostgreSQL 並 initdb，埠號 5433）→ serve.py（從 8000 開始找空閒埠，開啟瀏覽器）→ uvicorn 載入 app.main。

  2. 2寫 DB建表、種子資料、匯入機型

    boot_db 依序做三件事：

    ① create_all 建立所有資料表。

    ② seed_all 寫入初始資料：管理員 admin@local（首次登入必須改密碼）、nlu／reply 提示詞 v1、模型設定（從 .env 帶入 DeepSeek）、軟體畫像（例如 Premiere Pro）、規則、閾值、追問卡。

    ③ laptops 表是空的時候，用 importer.all_records() 從 CSV 匯入 371 台（同時算好各維度分數）。

  3. 3程式管理員登入

    /api/auth/login 用 bcrypt 比對密碼，成功後發 JWT（HS256，有效 14 天），寫進 HttpOnly Cookie lg_session。如果 must_change_password 為真，就必須先改密碼。後台 API 都要通過 require_admin，observer 角色呼叫寫入功能會被 forbid_observer 擋下（回 403）。

  4. 4讀 DB查看某一輪的鏈路

    AdminApp 呼叫 /api/admin/runs/{rid}，讀出案例 1 寫進 runs 的記錄，再用 trace.ts 的 11 步定義畫成鏈路追蹤圖：每一步的耗時、模型呼叫、命中規則、需求檔案的前後差異。

  5. 5LLM模型設定頁測試連線

    ModelPage.tsx → /api/admin/models/{id}/test → llm.test_connection，送出「只回復：pong」確認金鑰和網址可用。也可以把 nlu 和 reply 兩個槽位指派給不同的模型（/models/assign）。

  6. 6寫 DB上傳新 CSV 並發佈

    發佈時會先清空 laptops 再重建，並在 change_logs 寫一筆「發佈數據 vX」（記下前後台數）。
