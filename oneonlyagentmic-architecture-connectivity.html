OneOnlyAgentMic 架構與連線

Android 手機錄音，交給你自己的 Windows 11 桌機做 ASR 和 Agent 分析。本頁比較系統架構和手機↔桌機連線方案，並給出建議。查證日 2026-10-31；速度與準確率多為廠商自報，都還沒在目標硬體上實測。

結論架構方案推薦架構桌機算力連線方案驗證計畫來源
結論
架構：批次工作管線手機上傳分段，桌機排隊處理，手機再取回結果。桌機離線也不影響錄音。
連線：區網 → iroh → Tailscale同網段走區網；遠端首選 iroh；iroh 的 PoC 不過就用 Tailscale。
算力：依硬體分層ASR 預設走 CPU，LLM 走 Vulkan。8GB 直接呼叫 llama-server，16GB 以上才用 opencode。

A 批次工作管線

推薦

優點

  • 桌機關機、斷網都不影響錄音
  • 每段都有 ACK，音檔不會誤刪
  • 可在手機顯示每個處理階段
  • 記憶體小的機器也能靠排隊完成

缺點

  • 結果有延遲，不能邊講邊看
  • 上傳協定和工作狀態要自己實作

B 同步資料夾

僅適合原型

優點

  • 開發量最少
  • Syncthing 全程端對端加密
  • 雙向同步很貼近「音檔過去、結果回來」

缺點

  • 官方 Android 版已於 2024-12 封存
  • 社群 fork 活躍，但有維護者交接爭議
  • 「確認後才刪檔」要另外補
  • 中繼速度遠低於直連

C 即時串流

後續選配

優點

  • 可做即時字幕
  • 對話中就能看到重點

缺點

  • 桌機離線或網路差就失效
  • 耗電最高，背景連線也最不穩
  • ASR 持續佔用記憶體，8GB 機種難以負擔

常駐服務建議用 Rust，因為 iroh 本身是 Rust。ASR 和 LLM 都以獨立子程序執行，工作結束就退出，記憶體可以完整釋放，崩潰也不會拖垮常駐服務。

如何使用桌機算力

目前沒有穩定、跨廠商、又不綁 Windows 版本的 ONNX GPU 路線，所以 ASR 預設走 CPU，LLM 走 Vulkan。第一次啟動時要實測再決定，因為 Radeon 內顯跑 LLM 可能比 CPU 慢。

硬體（門檻為推論）ASR語者分離分析
8GB、內顯或純 CPUQwen3-ASR 0.6B int8；更低階用 SenseVoice3D-Speaker + seg3，可關閉直接呼叫 llama-server + Qwen3.5 2B q4
16GB，或獨顯 4–6GBBreeze-ASR-25 Q5，或 Qwen3-ASR 1.7B同上opencode + 7–14B 模型，需實測
NVIDIA 8GB VRAM 以上Breeze + faster-whisper CUDApyannote community-1opencode + 更大模型
Intel Arc 或 Core Ultra可選 OpenVINO Whisper同第一層Vulkan 或 OpenVINO
任何硬體，且同意上雲同上同上opencode + 雲端模型，品質最穩，但逐字稿會離開桌機

為什麼 8GB 不走 opencode

  • Ollama 官方寫 opencode 需要 64k 以上 context，opencode 文件建議 16–32k
  • 小模型常見不呼叫工具的回報（#25352、#51268）
  • 這一步只是「讀逐字稿、輸出 JSON」，一次呼叫就能完成

opencode 的使用限制

  • 官網文件多對應 v1；v2 原始碼查無結構化輸出，改用 MCP 工具回傳 JSON
  • 逐字稿可能夾帶指令，必須禁用 bash、webfetch、websearch
  • 官方建議 WSL，原生 Windows 要實測
  • 用 opencode run 逐次執行，外層加 timeout 與重試
第二部分

手機↔桌機連線方案

資料量比想像中小：16 kHz Opus 24 kbps 每小時約 10.8 MB，8 小時約 86 MB，走 2 Mbit/s 中繼約 7 分鐘傳完。所以穩定性和設定難度比帶寬重要，批次同步也不需要低延遲。

iroh

首選，PoC 通過後定案

優點

  • 掃一次 QR 就配對，不用帳號或另一個 App
  • 不佔 VPN 槽，可同時開公司 VPN
  • 官方有 Kotlin 綁定，也支援 Windows x86_64
  • 週期性連線、傳完就關，符合官方對 Android 背景的建議（推論）

缺點

  • Maven 版不含 Android，要用 NDK 自行編譯
  • 有第三方回報 async 呼叫在 Android 卡住（未驗證，必測）
  • 公共中繼限速、無保證，官方不建議用於生產
  • 開源專案沒有人替所有使用者付中繼費

Tailscale

備援，現在就能用

優點

  • 工程量最小，App 只要連到一個位址
  • NAT 穿透成熟，打不通時有 DERP 保底
  • Windows 和 Android 都有官方 App

缺點

  • 要裝 App、註冊帳號，還會佔 VPN 槽
  • 依賴 Tailscale 公司的控制面
  • Personal 方案限非商用
  • DERP 官方案例僅 2.2 Mbit/s，但批次音檔仍夠用

區網直連

必備

優點

  • 最快，不經第三方
  • 適合回家後整夜批次同步

缺點

  • 只在同網段有效
  • Android 17 起 target 37 要處理 ACCESS_LOCAL_NETWORK

FRP + VPS

進階選項

優點

  • 行為單純，手機走一般網路，不佔 VPN
  • 可全權掌控，Apache-2.0

缺點

  • 要租 VPS 並維護，等於自架中繼，與目標衝突
  • 端點公開，認證和 TLS 要自己處理
  • 部分防毒會誤報 frpc

Cloudflare Tunnel

進階選項

優點

  • 桌機只需對外連線，不用開埠
  • 手機就是一般 HTTPS，背景行為最單純

缺點

  • 穩定網址需要自己的網域
  • 免費方案單請求上限 100 MB，要分段
  • HTTP 流量會在 Cloudflare 解密，音檔必須另外加密
  • 條款對大量音訊的適用方式未確認

純 WireGuard

進階選項

優點

  • 無第三方依賴
  • 直連速度最好

缺點

  • 要設定路由器、DDNS 或公網 IPv6
  • IPv4 在 CGNAT 後無法運作
  • 對非網路專家不實際
不建議的方案原因
Headscale需要公開伺服器，等於自架中央控制面
NetBird、ZeroTier可用，但對本專案沒有勝過 Tailscale 的明顯優勢；ZeroTier 中繼慢
libp2pIMC 2026 論文量到打洞成功率 70% ± 7.1%（非手機專測），Relay v2 也不適合傳檔保底
WebRTC仍要信令與 TURN，會把中央服務帶回來
Syncthing見架構方案 B

為什麼這樣排序

App 依序嘗試區網、iroh、使用者設定的位址，三者共用同一個傳輸介面。iroh 是唯一同時做到免帳號、免 VPN App、免公開伺服器、不佔 VPN 槽，又有官方 Android 綁定路徑的選項。主要風險是 Android 綁定成熟度和中繼。如果想最快做出第一版，就先用 Tailscale 上線，之後再補 iroh。

沒有方案能完全不依賴他人的基礎設施。區網和 WireGuard 不靠第三方，但只適用部分網路環境。iroh 和 Tailscale 靠第三方協助建立連線，內容仍加密。FRP 和 Headscale 則要自己維護伺服器。

你的情況建議
一般使用者iroh（PoC 後）；目前可先用 Tailscale
需要同時開公司 VPNiroh
公司網路封鎖 UDPTailscale DERP 或 Cloudflare Tunnel（需實測）
想完全自主已有 VPS 就用 frp，或自架 iroh 中繼
大多在家同步區網直連即可

PoC內容通過條件
