方案 B 架構詳解

TypeScript 模組化單體＋共用決策引擎。前提：每天 10,000 人、每人 10 則訊息；要能接很多家語言模型，並找出「效果／成本」最好的模型；以最好的建法為目標，保留未來改進的空間。

標記說明： 建議 我推薦的做法； 假設 我先用的數字或前提； 待確認 需要你決定。
價格、市場、語言轉換依你的要求不在本文討論範圍。不懂的名詞可以先看最後的名詞小辭典。

0. 一頁看懂

一句話：把 Demo 的 engine.js 整理成一個 TypeScript「決策引擎套件」，伺服器、使用者網頁、後台三處共用同一份；語言模型只負責「聽懂使用者」和「把結果說成人話」，推薦哪一台永遠由引擎決定。

  • 4 個應用程式：使用者網頁、後台網頁、API 伺服器、背景工作程式（worker）
  • 3 個資料服務：PostgreSQL（主資料庫）、Redis（排隊、限流、快取）、物件儲存（大檔與模型完整紀錄）
  • 核心套件：決策引擎、共享契約（資料格式）、模型閘道、評測工具、功能開關
  • 每一輪對話都記下 6 個版本號（引擎、規則、資料、提示詞、模型路由、功能開關），所以任何一輪都能完整重現
  • 模型評測平台：同一批測試題丟給多個模型，自動算出「準確度、速度、成本」，畫成排行榜；線上還能做影子測試和 A/B 分流

1. 設計原則（排序即優先順序）

#原則落實方式
1程式決定事實，模型只負責理解與表達語言模型只輸出「需求變更 JSON」和「回覆文字」；推薦、排序、門檻全由引擎計算；回覆裡的數字要核對過才能送出
2一份引擎，到處共用引擎是純函式套件，沒有網路、資料庫、時間、亂數的副作用；伺服器、使用者網頁、後台、worker 都 import 同一版
3每一輪都能重現對話只存「輸入」；每輪記錄 6 個版本號；同樣的輸入和版本一定得到同樣的推薦
4模型可以隨時換、隨時比所有模型走同一個閘道介面；路由設定放資料庫，後台改了就生效，不用改程式
5每個細節都有開關統一的功能開關系統，支援依比例、依測試群組開啟，並記錄在每一輪
6先單體、留好拆分的縫一個 API 程式、模組之間只透過介面溝通；未來流量大了，模型閘道或 worker 可以獨立拆出去
7模型壞了，系統不能壞每個模型呼叫都有逾時、重試、備用模型，最後還有「規則版理解＋模板文案」保底

資料庫寫入每輪約 8 列（訊息×2、執行、模型呼叫×2、狀態、卡片事件…）→ 尖峰約 80 列／秒一台中型 PostgreSQL 很輕鬆
資料量資料庫每輪約 3 KB → 每天約 0.3 GB；模型完整請求／回應每輪約 12 KB，壓縮後放物件儲存資料庫每月約 10 GB，大表按月分區
真正的瓶頸是語言模型供應商的速率上限，不是你的伺服器。每分鐘 2,400 次呼叫、400 萬 token，很多供應商的基本方案撐不住。對策：
  • 申請較高等級的額度；同一家準備多把金鑰
  • 主備模型分屬不同供應商
  • 「混合理解」：規則就能完全聽懂的訊息不呼叫模型（見第 7 節），預估可省下 30–60% 的理解呼叫 假設，需實測

6. 決策引擎（packages/engine）

它是整個系統的心臟。輸入「需求檔案＋設定＋機型資料」，輸出「候選分組、分數、下一步動作、卡片資料、解釋」。

從 Demo 移植的部分改進
evaluate、rank、weightsFor拆成「門檻」「權重」「評分」三個檔案，每條門檻有固定的原因代碼（例如 BUDGET_OVER），方便統計和顯示
decideAction、nextKey、matters規則順序做成設定裡的清單，後台可調整；每次決策輸出「命中哪一條規則」
picksFor、closeCall、relaxOptions推薦組合和放寬選項各自獨立，方便做開關
explain直接產出後台「為什麼這樣回答」所需的完整結構
模組層級的 S、CFG改成每次呼叫都把狀態和設定當參數傳進去，不再有共享變數，伺服器同時處理很多人也不會互相干擾
Demo 用亂數產生的機型和影片時間點移除；資料一律從資料庫的機型快照傳入

主要函式（示意）：

  • applyInput(state, input, ctx) → { state, turnResult }：處理一次輸入（說話、點選項、排除機型、放寬…），等同 Demo 的 step
  • rank(profile, ctx) → { ok, border, out, evals, weights }
  • decide(state, ctx) → action：追問／確認／放寬／推薦
  • buildCards(state, action, ctx) → cards：卡片資料，每個數字附上實測出處 ID
  • explain(state, ctx) → explanation
  • replay(inputs[], ctx) → turns[]：用輸入清單重跑整段對話

ctx（情境）＝規則設定＋機型資料快照＋開關值＋引擎版本。同樣的 ctx 和輸入，一定得到同樣的結果。

機型資料怎麼給引擎：機型只有幾百台，整份資料不到 1 MB。API 啟動時把「目前發布的資料版本」整份載入記憶體；後台發布新版本時，各台 API 透過 Redis 收到通知，重新載入。引擎評分不需要每次查資料庫，所以很快。

各階段說明與時間預算

階段做什麼預算失敗時
1 對話總管驗證訪客或使用者身分；每人每分鐘限 10 輪；同一個 client_request_id 只處理一次；同一對話同時只跑一輪（第二個請求回 409）50 ms回明確錯誤碼
2 需求理解「混合模式」：先跑規則解析；規則有聽不懂的字詞才呼叫模型。模型只回 JSON，每個欄位要附「原文依據」，依據不在原文裡就丟掉規則 10 ms／模型 2,500 ms格式錯重試 1 次 → 換備用模型 → 只用規則結果，並請使用者補充
3 詞庫與攔截別名正規化、軟體門檻展開、未收錄機型攔截20 ms—
4–6 引擎計算門檻篩選、權重、評分排序50 ms這裡出錯＝程式錯誤，回錯誤，絕不亂推薦
7 動作決策追問、確認、放寬、推薦、比較、解釋50 ms—
8 卡片資料組出卡片內容，每個數字附實測 ID 和影片時間點20 ms—
9 回覆生成模型只拿到第 8 步的事實；逐句串流；每句的數字要能對上事實，對不上就刪掉該句首字 1,500 ms逾時或刪到不剩一句 → 用模板文案
10 寫入紀錄一個資料庫交易寫完；模型完整請求和回應壓縮後非同步送物件儲存60 ms寫入失敗要告警，但已送出的回覆不撤回
延遲目標：送出到看到結果卡片 P50 ≤ 1.5 秒（不用模型時 ≤ 0.3 秒）；送出到第一個字 P50 ≤ 3 秒、P95 ≤ 6 秒 假設，依模型實測調整。使用者直接改需求檔案或權重時完全不呼叫模型，P95 ≤ 0.5 秒。

斷線與重新整理

  • SSE 斷線時，前端呼叫 GET /conversations/{id}/state 拿最新狀態，不補播動畫
  • 若該輪還在跑，前端可用 GET /runs/{runId}/events?after=序號 接續收事件（事件暫存在 Redis 5 分鐘）

  • reply：回覆文字，要串流、語氣自然
  • judge：評測時的評審模型，固定一個高品質模型
  • 未來可加：summary（對話摘要）、classify（意圖分類）

路由設定（存在資料庫）

  • 每個角色：主模型、備用模型清單（依序）
  • 分流比例：例如 nlu 90% 走 A、10% 走 B（A/B 測試）
  • 影子模型：另外跑一份但不給使用者看，只記錄比較
  • 參數：溫度、最大 token、逾時秒數
  • 依對話 ID 雜湊分流，同一段對話固定用同一個模型
機制做法
統一介面generateObject(role, schema, messages)、streamText(role, messages)；回傳統一格式（內容、token、耗時、供應商、模型、成本）
結構化輸出用 Zod schema 要求 JSON；支援原生 JSON 模式的模型就用原生，不支援的用提示詞＋驗證
逾時與重試依角色設定逾時；網路錯誤或 429 才重試，最多 1 次，帶隨機退避
熔斷某供應商 1 分鐘內失敗率超過門檻就暫停 30 秒，直接走備用
多金鑰輪替同一供應商可設多把金鑰，分攤速率上限
計量模型單價表存資料庫，每次呼叫算出成本；提示詞快取命中也要記
紀錄資料庫存摘要（模型、token、耗時、成本、是否合格）；完整請求和回應壓縮放物件儲存，保留 90 天 假設
新增模型相容 OpenAI 格式的模型：後台填網址、模型名、金鑰即可；其他格式：寫一個轉接器（約 100 行）

9.3 怎麼判斷「效果／成本」最好

  • 散佈圖：橫軸是每千輪成本，縱軸是綜合效果分。最左上方那條邊界（帕累托前緣）上的模型才值得考慮，其他的都有「更便宜又更好」的替代品
  • 綜合效果分＝結果一致率 50%＋欄位 F1 20%＋回覆品質 20%＋格式合格率 10% 權重是假設，後台可調
  • 硬門檻：格式合格率 < 98% 或 P95 > 4 秒的模型直接不列入 假設
  • 理解和回覆分開選：理解要準、要快；回覆要自然。兩者最佳模型常常不同

A/B 分流依對話 ID 分組，5% → 20% → 50% 逐步放大拿到建議的比例、對話中途離開率、按讚率、重問率、成本、延遲

11. 功能開關與實驗

專案要求「每個細節都有開關，方便找真實使用者測試」。開關分成兩種，一定要分清楚：

引擎開關（會影響推薦）

例如：確認卡要不要出現、追問上限、「兩台很接近」提示、放寬選項數量、某條門檻規則。

  • 屬於 rule_version 的一部分
  • 改了要走回歸測試和影響評估
  • 重跑舊對話時會用當時的值

介面開關（只影響畫面）

例如：顯示效能數字、顯示影片時間點和連結、卡片樣式、動畫、版面配置。

  • 屬於 flags_version
  • 可以即時切換，不影響推薦結果
  • 適合大量 A/B 測試
功能做法
開關定義每個開關有：代碼、說明、類型（開關／選項／數字）、預設值、屬於哪種
目標設定全部開、全部關、依比例（例如 30%）、指定測試群組（例如「訪談用戶 A 組」）、指定訪客 ID
穩定分組同一訪客永遠落在同一組（依 ID 雜湊），不會一下有一下沒有

實驗報表選一個開關，自動比較各組的拿到建議率、離開率、按讚率、對話輪數，並標示差異是否顯著

為什麼「送訊息的回應直接就是串流」：處理這一輪的伺服器就是推送的伺服器，不需要在多台伺服器之間轉發事件，架構最簡單。以每秒 20 輪、每輪 6 秒計算，同時只有約 120 條連線，Node.js 輕鬆應付。

18. 安全

  • 金鑰：模型 API 金鑰只放雲端密鑰管理服務；後台只顯示末四碼，不能匯出
  • 後台登入：強制兩步驟驗證（或接公司 Google／Microsoft 帳號登入）；角色分管理員、編輯者、唯讀；所有修改寫稽核紀錄
  • 使用者端：訪客用匿名代碼（放 HttpOnly Cookie）；輸入最長 1,000 字；每人每分鐘最多 10 輪；同一 IP 另有上限
  • 提示詞注入：模型的輸出只能是通過驗證的 JSON 或經過數字核對的文字；模型沒有任何權限呼叫工具或查資料庫，所以就算被注入也改不了推薦結果
  • 隱私：送給模型的內容不含任何個人識別資料；依保留政策去識別化；提供刪除對話的入口
  • 依賴套件：自動掃描漏洞（GitHub Dependabot）

19. 測試策略

層級測什麼何時跑
Demo 一致性測試用 Demo 原本的 engine.js 和新引擎跑同一批（數千段）自動產生的對話，第一名、動作、分數必須一致。這是移植引擎時最重要的安全網每次推送
引擎單元測試每條門檻、權重、決策規則都有測試；用固定機型資料每次推送
回歸用例整段對話 → 期望第一名與動作每次推送、每次發布設定
契約測試API 輸入輸出、SSE 事件都符合 Zod 定義每次推送
整合測試API ＋真的 PostgreSQL（Testcontainers）＋假的模型每次推送
端到端測試Playwright 跑 Demo 的三個示範情境部署到測試環境後
模型評測（小）50 題理解題，確保提示詞改動沒有退步改提示詞時
模型評測（完整）全部資料集 × 所有候選模型每週、手動
壓力測試k6 模擬每秒 20 輪（用假模型＋真模型各跑一次）上線前、重大改版前
故障演練關掉主模型、讓資料庫變慢，確認備援和保底文案正常上線前

附錄：名詞小辭典

名詞白話解釋
API網頁和伺服器之間的「點餐窗口」，網頁照規定格式點餐，伺服器照規定格式出餐
SSE（伺服器推送事件）伺服器可以一段一段把結果推給網頁，像看文字慢慢打出來
單體／模組化單體整個後端是一個程式，但內部分成界線清楚的模組；比拆成很多小服務簡單
Monorepo多個程式放在同一個程式碼倉庫，方便共用套件
純函式同樣的輸入永遠得到同樣的輸出，不偷偷讀寫外部東西
ORM用程式語言的寫法操作資料庫，不用手寫每一句 SQL
遷移（migration）資料庫結構的變更紀錄，照順序執行就能把資料庫升級到最新
佇列（queue）待辦清單；耗時的工作先放進去，由 worker 慢慢做
Redis速度極快的記憶體資料庫，適合放暫存資料、計數器、佇列
物件儲存像雲端硬碟，放大量檔案，便宜但不適合查詢
冪等同一個請求送兩次，結果和送一次一樣（防止網路重送造成重複訊息）
熔斷某個服務一直失敗時先暫停呼叫它，避免拖垮整個系統
結構化輸出要求語言模型只回固定格式的 JSON，程式才能可靠地讀
影子模式新模型在背後偷偷一起跑，結果只記錄不給使用者看
A/B 測試使用者隨機分組，各組用不同版本，比較哪一版效果好
金絲雀發布新版本先給一小部分人用，沒問題再全面開放
帕累托前緣在「效果」和「成本」之間取捨時，那些「沒有別人比它更便宜又更好」的選項
蒸餾用大模型的答案訓練小模型，讓小模型學到接近的能力
P50／P9550%／95% 的請求在這個時間內完成；P95 代表「最慢的那 5% 有多慢」
容器（Docker）把程式和它需要的環境打包成一個盒子，到哪裡都能一樣地執行
CDN把網頁檔案放到世界各地的伺服器，使用者從最近的地方下載
OpenTelemetry記錄「一個請求經過哪些步驟、各花多久」的開放標準
