1. 我做了什麼（審查方法）

這份報告不是只讀文件，而是實際執行與量測：

  1. 跑完兩邊全部測試：A 後端 834 個、前端 243 個全過；B 單元與 API 測試 681 個全過，另外 47 個 Playwright 真瀏覽器測試也全過（2.5 分鐘）。
  2. 型別檢查與正式建置：兩邊 tsc 皆通過，B 另跑 vite build 取得真實打包尺寸。
  3. 離線一輪對話效能基準：同樣 5 句話 × 3 輪，不叫模型，量每輪耗時與回應大小。
  4. 靜態量測：檔案與函式長度、any 數量、裸例外、原始 SQL、TODO、死碼等。
  5. 五位獨立審查員（子代理）逐檔閱讀：A 後端、A 前端、B 後端、B 前端各一份深度審查，加上一份「功能完整度對照表」；每條發現都附檔名與行號。我再對其中最嚴重的指控親自開檔驗證（例如 A 的 updated_at 從未更新、事件端點不需登入即可寫庫，皆屬實）。

3. 七個面向逐項比較

3.1 程式碼品質 → B 明顯較好

A 的問題集中在「越加越大、沒有回頭清理」
  • backend/app/api.py 一個檔 3,009 行、120 個函式、79 個端點；新功能已改放 routers/，舊檔沒拆。
  • pipeline.py 的 _run_turn 單一函式 712 行，是整套系統的心臟；超過 100 行的函式共 13 個。
  • 前端 tsconfig.json 寫著 "strict": false，等於關掉 TypeScript 最重要的保護；非測試程式碼裡 any（放棄型別）超過 540 處；UserApp.tsx 單一元件 860 行、42 個狀態變數。
  • 確認為不可達的死碼：後台約 300 行舊頁面、對話卡 5 個舊分支、永遠是空的 SOFT_MAP、兩個內容完全相同的端點。
  • 重複：「金額格式化」函式寫了 8 次，七維中文標籤表寫了 6 次且互不一致（同一畫面可能出現「螢幕」與「屏幕」、「擴充性」與「擴展性」）。
  • 註解大量引用內部工單編號（W1～W20、K1～K5、A7-4…），沒有規格文件在手讀不懂為什麼。
  • 兩邊都沒有 ESLint 之類的 lint 工具。
B 的狀況
  • strict 與 noUncheckedIndexedAccess 全開，後端 any 為 0，前端非測試程式碼也接近 0；console.log、TODO、@ts-ignore 皆為 0。
  • 檔案都在 400 行以下，評分引擎每檔 50～180 行、職責單一。
  • 缺點：行寬過長（routes-admin.ts 最長一行 850 字元、turn.ts 有 33 行超過 160 字元）、turn() 單函式 167 行、Zod 驗證結構與手寫型別平行維護造成 36 處型別斷言、方案頁的增刪改程式在兩頁幾乎複製。

3.2 強健性 → B 較好，但兩邊都有同一個前端競態

兩邊共同的缺陷：使用者送出一句話、在等待回覆期間切換到另一個對話，舊對話的回覆會寫進新對話的畫面。A 在 UserApp.tsx 的 send()、B 在 useAssistant.ts 的 applyTurn() 都沒有比對回應屬於哪個對話。
A 獨有的問題
  • 同一對話沒有任何併發保護：兩個請求同時進來會各自讀同一份需求檔案、後寫入者整份覆蓋，前一句話的需求會消失。
  • 確認的功能 bug：pipeline.py:1476 寫著 conv.updated_at = conv.updated_at（等於沒更新），而且全專案沒有別處更新它。後果是 expire_idle 會在對話建立 30 分鐘後無條件把進行中的對話標成已結束，對話列表排序也是錯的。
  • 啟動時在模組載入階段就跑建表、補欄、種子、重算分數，任何一步失敗整個服務起不來；多 worker 會重複執行。
  • 52 處 except Exception 吞掉錯誤，全部後端只有 6 處有寫日誌；例如即時算分失敗會默默退回舊分數，前端看不出來。
  • 兩個端點直接吃任意字典（payload: dict）不驗證。
B 的優點與缺口
  • 所有請求 body 用 Zod 驗證、錯誤格式統一為 { error: "中文訊息" }；同一對話同時兩句話，第二句回 409（有測試）。
  • 模型失敗的降級鏈完整：規則抽取兜底、模型回覆要過六道事實核對（編造數字、外部網址、張冠李戴、漏講弱項…任一不過就退回模板句）、三個入口「永不丟錯」並有測試。
  • 缺口：前端沒有錯誤邊界（任何渲染例外都是白頁）；併發保護只存在單一行程的記憶體；啟動不檢查資料庫是否已升級，舊資料庫會在使用者講第一句話時才 500；後台設定寫入沒有數值範圍與 key 白名單。

A 的模型降級鏈同樣完整（主模型→備用模型→關鍵詞規則→模板句），這點兩邊都做得好。

3.4 架構設計 → B 明顯較好

B 的依賴方向嚴格單向：contracts（型別、預設值、驗證、開關清單）← engine（評分、權重、追問、理由，零 I/O 純函式）← nlu／db ← api；前端只依賴 contracts。意思是：前後端用的是同一份型別與驗證，後端改了欄位、前端編譯就會報錯；後台表單直接重用後端那份驗證函式。

A 的分層是「路由直接操作資料庫 → pipeline 編排 → 純函式模組」。純函式核心（權重推導、評分、理由）的紀律其實不錯，也能離線重現；但：

  • 前端型別全部手寫、與後端沒有任何共用，核心資料結構（機型、訊息、快照、卡片）在前端全是 any。
  • 靠 20 處「函式內延遲匯入」掩蓋 pipeline↔followup↔software_cards↔profile_view 之間的循環依賴。
  • CSS 是用 Python 腳本機械式加前綴把兩個 demo 網頁的樣式硬合併，產生兩個 30KB 的單行檔，同一個選擇器散在 4～6 個檔案。
  • 前端沒有路由：對話 id 與後台頁碼都不在網址上，重新整理就回首頁。B 的對話 id 在網址上。
兩邊都做得好的：功能開關系統。A 的開關註冊表更強（型別、範圍、列舉、公開/私有區分、舊鍵遷移、每輪一次讀取），B 的開關較簡單但「加一行就出現在後台、每個開關都有『關掉就不渲染』的測試」。

4. 兩邊各自最該先修的五件事

若選 A 繼續
  1. 金鑰明文儲存。
  2. 同一對話無併發保護；updated_at 從不更新導致 30 分鐘自動結束對話。
  3. 前端打開 strict、清掉 540 多處 any、刪除約 300 行死碼。
  4. 拆分 3,009 行的 api.py 與 712 行的 _run_turn。
  5. 補真實 PostgreSQL 測試與瀏覽器測試；修後台全表載入與 N+1。
若選 B 繼續
  1. 前端加錯誤邊界；修切換對話時的回應競態（A 也有）。
  2. 啟動時檢查資料庫版本，不一致就拒絕啟動並提示執行 pnpm setup。
  3. 後台設定寫入加 Zod 範圍與 key 白名單；把寫死的推薦係數（0.6／0.4／0.3／-1）搬進閾值頁。
  4. 回應瘦身（只對前 K 名產生理由文字、開 gzip）；llm_calls 加索引。
  5. 限流補齊、模型網址擋內網；視需要把併發鎖改為資料庫樂觀鎖。

B 的五件事都是幾十行的局部修補；A 的前四件是結構性工程。

5. 建議：以 B（v1.0.8）為基底，把 A 當規格來源

5.1 為什麼

  1. 修地基比搬功能貴。A 的問題（單體檔案、關閉型別檢查、金鑰明文、無併發控制、無真資料庫測試）每一項都要大動，而且改的時候沒有型別與瀏覽器測試保護，很容易改壞。B 的問題多數在一個小版本內可修完。
  2. A 的功能領先是「可轉移的」。A 多出來的東西，規格都寫在 docs/v0.0.5-規格/（K1 權重系統、K2 分數計算、K3 高級權重、K4 軟體畫像、K5 理由追問、A 後台、U 使用者端、開關總表），而且 A 的核心演算法是純函式、有黃金測試可當「對答案」的基準。搬進 B 時可以逐功能比對輸出。
  3. 對開發新手更安全。B 的每次修改都有 strict 型別檢查、前後端共用契約（後端改欄位前端立刻編譯錯）、真瀏覽器測試三層保護。A 的前端是 strict: false＋any 到處都是，改壞了要到執行時才知道。
  4. 單一語言、單一工具鏈。B 全部 TypeScript，一個 pnpm 指令跑完測試、型別檢查、建置；A 要同時維護 Python（uv）與 Node（npm）兩套環境，Mac 上還有「venv 跑到舊版直譯器」這類坑（README 已記錄）。
  5. 效能底子好。一輪 14 ms 對 117 ms、使用者端首次載入 123 KB 對 213 KB（gzip），之後再往上加功能有餘裕。

5.2 要誠實說的代價

  • 功能要補很多版。以 A 的功能清單估計，把評分核心（K1～K3）、軟體畫像 2.0（K4）、後台告警／資料品質／洞察／管理員管理、指名查詢與 @ 比較都搬過來，大約是 6～10 個小版本的工作量。
  • Windows 一鍵啟動要重做。A 的 .bat 與 PostgreSQL 自動下載邏輯在 B 不存在；若近期要交付 Windows 使用者，這是 B 的硬缺口。
  • A 的後台可調性（訊號表、子權重表、正規化選項都能在後台改）是 B 目前沒有的，而這正是「找真實使用者調參數」最需要的。建議列為搬遷的第一優先。

5.3 建議的搬遷順序（供下一步討論）

順序搬什麼理由
1先修 B 的五件事（第 4 節）地基補強，之後每一步都站得穩
2K1 權重帳本＋訊號表＋強度係數（後台可編輯）「程式決定事實、每一分有來源」是產品核心，也是後續理由、追問的基礎
3K2 三種正規化＋平手門檻＋同價位性價比直接影響排序結果，且 A 有黃金測試可對答案

5K4 軟體畫像 2.0＋13 套軟體＋消歧義卡設計類使用者的主要場景
6後台：告警、執行回放（token／成本）、資料品質三態、多管理員上線前必要

5.4 什麼情況下應該反過來選 A

只有一種：近期（例如兩週內）必須把功能完整的版本交到 Windows 使用者手上做測試，而且暫時不打算再大改。那麼 A 現成可用，但請至少先修金鑰明文與 updated_at 兩個 bug。若之後還要持續開發半年以上，仍建議回到 B。
