4. 一輪對話怎麼跑、資料怎麼流

使用者端的一輪對話：

  1. 使用者輸入文字，或點選卡片上的選項
  2. send(inp) 把這次輸入加進 script（輸入清單）
  3. 呼叫 ENG.step(sess, inp, CFG)，引擎算出這一輪的結果（turn）
  4. 重新繪製對話區和結果區
  5. 把對話存進 localStorage

重點：對話「只存輸入」。存下來的只有輸入清單，重新打開時用 runAll() 把所有輸入重跑一次，就能還原出狀態。

後台：讀同一個 localStorage 裡的真實對話，加上模擬對話，用目前規則或草稿規則重跑（replay、impact），算出改規則前後的差異。

設定同步：後台改設定後寫進 lpa9-cfg；使用者頁透過瀏覽器的 storage 事件馬上套用。

四、候選方案

三個方案最大的差別：引擎放在哪裡跑、要不要維護兩份引擎。

方案 A：靜態前端＋雲端函式＋託管資料庫（例如 Supabase）

複雜度：低擴展性：低～中推薦 ★★☆☆☆

適用：快速上線、驗證市場、用戶少。

模組劃分：

  • 使用者頁和後台都是靜態網站，引擎照舊在瀏覽器裡跑
  • 雲端函式只做兩件事：呼叫語言模型（隱藏 API 金鑰）、寫入紀錄
  • 託管 PostgreSQL 存設定、對話、機型

資料流：瀏覽器向雲端函式取得語言模型理解的需求 → 引擎在本機算出推薦 → 把輸入和結果寫入資料庫。

優點
  • 幾乎直接沿用 Demo
  • 開發最快、成本最低
缺點
  • 規則和整個機型庫暴露在前端
  • 推薦在使用者瀏覽器算出，伺服器無法保證和紀錄一致
  • 後台 60 天重跑在瀏覽器跑，資料多會很慢
  • 很難做「數字核對」這種只能在伺服器做的步驟
推薦

方案 B：TypeScript 模組化單體＋共用引擎套件

複雜度：中擴展性：中～高推薦 ★★★★★

適用：要正式上線，又要保留「使用者頁和後台用同一份引擎」這個核心設計。

模組劃分（同一個程式碼庫，用 monorepo 管理）：

  • engine：把 engine.js 改寫成 TypeScript 純函式套件，前後端共用
  • api：Node 後端
    • 對話總管：接收訊息、編號、同一對話同時只跑一輪
    • 語言模型閘道：需求理解、回覆生成、供應商主備切換
    • 數字核對
    • SSE 推送
    • 後台 API
  • worker：背景工作——重跑影響評估、回歸用例、價格同步、資料品質檢查、告警
  • web-user、web-admin：兩個前端；後台的試算和預覽直接在瀏覽器呼叫同一個引擎套件
  • PostgreSQL：沿用 Demo 那 17 張表的設計

資料流：使用者訊息 → api → 語言模型抽取需求 → 引擎決定推薦 → 語言模型寫回覆 → 核對數字 → SSE 推回前端 → 寫入執行紀錄。
後台改規則 → 存成草稿 → worker 重跑歷史對話 → 看影響 → 發布新版本。

優點
  • 引擎只有一份，結果可重現；後台預覽和線上保證一致
  • Demo 程式碼可以搬過去改寫，不必重寫邏輯
  • 全部 TypeScript，一種語言，學習負擔最低
缺點
  • 要把約 1,450 行壓縮過的程式碼整理成型別清楚的模組，並補測試
  • 資料分析能力不如 Python 生態系

方案 C：Python 後端（例如 FastAPI）模組化單體＋React 前端

複雜度：中～高擴展性：高推薦 ★★★☆☆

適用：團隊熟悉 Python，或之後要做大量資料分析、機器學習。

模組劃分：

  • 把引擎改寫成 Python，放在後端
  • 前端只負責畫面；後台試算一律透過 API 呼叫後端
  • 背景工作同樣用 Python
優點
  • Python 的資料處理工具多（匯入 CSV、統計）
  • 呼叫語言模型的套件很成熟
缺點
  • 引擎要用另一種語言重寫，必須逐案比對結果和 Demo 一致，工作量和風險較高
  • 前端想即時預覽（例如拖動權重馬上看到清單變化），就得維護兩份引擎，或每次等伺服器
  • 前後端兩種語言，維護成本較高

五、我的建議：方案 B

你已選定 TypeScript（2026-10-29）。方案 A 和 B 都用 TypeScript；方案 C 需要 Python 後端，已不符合這個決定。
  1. Demo 最核心的設計是「同一份引擎、同一份設定、對話只存輸入、可以重跑」。方案 B 是唯一不必重寫引擎，又能把計算移到伺服器、保證結果可稽核的方案。
  2. 語言模型只負責「理解」和「表達」，程式決定推薦結果。這和專案 CLAUDE.md 的「程式碼決定事實，模型只負責理解與表達」一致；方案 B 用一個語言模型閘道和一個核對步驟就能把兩者隔開。
  3. 一種語言、一個程式碼庫。對新手、一人維護來說成本最低；所有功能開關都可以放在規則版本裡，由後台統一管理。
